# Terraform Permissions — Reference for IAM-role-holder edges

Companion to `edge-terraform-templates.md` (which covers the caller/service-
principal decision tree) and `terraform-resource-templates.md` (which covers
what a *node* emits on its own). This file is the detail reference for the
**IAM-role-holder** branch specifically: every resource that has
`permissionType: "IAM"` (Lambda, EC2, ECS...) needs its own `aws_iam_role`,
and every outgoing edge where it's the caller adds a policy statement to
that role.

## The two-resource split: identity vs. permissions

AWS splits "having an identity" from "what that identity can do" into two
separate resources on purpose, so permissions can be added or removed later
without ever touching the identity:

| Resource | Analogy | Created | Grows? |
|---|---|---|---|
| `aws_iam_role` | The ID badge itself — says "I am this Lambda" | Once, per IAM-role-holder node | No — fixed shape |
| `aws_iam_role_policy` | The list of doors that badge can open | Once per outgoing edge where this node is the caller | Yes — one more "door" per connection |

This is why `aws_iam_role` belongs in a service's own `create()` (a base
resource every IAM-role-holder always has, independent of any connection),
while `aws_iam_role_policy` content is generated by
`toTerraformEdgePropertiesCaller()` — see `edge-terraform-templates.md`.

### What generalizes across every IAM-role-holder, and what doesn't

| Piece | Generic (same mechanism for Lambda, EC2, ECS...)? | Notes |
|---|---|---|
| The `aws_iam_role` resource + its wrapper shape | Yes | Only the trust principal differs (`lambda.amazonaws.com` vs `ec2.amazonaws.com`) |
| The `aws_iam_role_policy` wrapper shape (`name`/`role`/`policy`) | Yes | Boilerplate, identical regardless of caller or counterpart |
| Which actions go inside the policy | **No** | Specific knowledge of "what API calls does *this* caller need against *this* counterpart" — e.g. Lambda→S3 needs `s3:GetObject`/`PutObject`; Lambda→DynamoDB needs different actions entirely |

Candidate shared helpers (plain functions, not a new class in the
`Resource` inheritance chain — matches how the rest of this codebase
composes rather than inherits):

- `makeIamRole(roleName, principalService)` → the `aws_iam_role` block,
  called once from each IAM-role-holder's `create()`.
- `makeIamRolePolicyStatement(roleLinkPath, actions, resourceArnExpr)` →
  the `aws_iam_role_policy` block, called from each IAM-role-holder's
  `toTerraformEdgePropertiesCaller()`.

## `aws_iam_role_policy` — Terraform argument reference

| Field | Required? | Type | Description |
|---|---|---|---|
| `name` | Optional | string | Name of the role policy. Random unique name if omitted. Conflicts with `name_prefix`. |
| `name_prefix` | Optional | string | Creates a unique name beginning with this prefix. Conflicts with `name`. |
| `policy` | **Required** | string (JSON) | The inline policy document — built via `jsonencode(...)`. |
| `role` | **Required** | string | The IAM role this policy attaches to — same-node `link` back to this node's own `aws_iam_role`. |

No separately exported attributes — this resource is a thin wrapper; all
the real content lives inside `policy`.

## IAM policy document JSON — `Version`

Only two valid values ever existed. **Always use `2012-10-17`** — AWS's own
guidance. The difference isn't which elements are legal (every element
below works identically in both); it's narrower than that:

| | `2008-10-17` | `2012-10-17` |
|---|---|---|
| Policy variables (`${aws:username}`, `${aws:SourceIp}`, etc.) | Not recognized — treated as a literal string | Substituted as intended |
| Everything else (`Sid`/`Effect`/`Principal`/`Action`/`Resource`/`Condition`) | Works the same | Works the same |

## IAM policy document JSON — `Statement` elements

| Element | Required? | Purpose | Value(s) |
|---|---|---|---|
| `Sid` | Optional | A label for the statement — no effect on evaluation | Any string you choose |
| `Effect` | **Required** | Whether the statement allows or denies | `"Allow"` or `"Deny"` — only these two |
| `Principal` | Required *only in trust/resource-based policies* | Who this statement applies to | `{"Service": "lambda.amazonaws.com"}` · `{"AWS": "<account-id-or-arn>"}` · `{"Federated": "<provider>"}` · or `"*"` for anyone |
| `NotPrincipal` | Optional, rare | Inverse of `Principal` | Same shapes as `Principal` |
| `Action` | Required, unless `NotAction` is used | Which API call(s) this statement covers | A string or array of strings, `"service:ActionName"` — wildcards allowed, e.g. `"s3:*"`, `"*"` |
| `NotAction` | Optional, rare | Inverse of `Action` | Same format as `Action` |
| `Resource` | Required *only in identity/permission policies* | What the action applies to | An ARN string or array of ARNs, or `"*"` |
| `NotResource` | Optional, rare | Inverse of `Resource` | Same format as `Resource` |
| `Condition` | Optional | Extra constraints on when the statement applies | A map: `{ "ConditionOperator": { "condition:key": "value" } }` — e.g. `{"StringEquals": {"aws:SourceAccount": "123456789012"}}` |

### `assume_role_policy` vs. the attached `aws_iam_role_policy` — mirror-image required fields

The two policy documents in play for any IAM-role-holder node use opposite
halves of the `Principal`/`Resource` pair:

| | `assume_role_policy` (trust policy, on `aws_iam_role`) | `policy` (permissions, on `aws_iam_role_policy`) |
|---|---|---|
| `Principal` | **Always present** — who may assume this role | Never present |
| `Resource` | Never present — the protected thing is the role itself, implicit | **Always present** — the ARN(s) this policy grants access to |
| `Action` | Always `"sts:AssumeRole"` | Whatever service actions the edge needs (`s3:GetObject`, etc.) |

### Worked example — Lambda's trust policy

```hcl
resource "aws_iam_role" "example" {
  name = "example-lambda-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect    = "Allow"
        Action    = "sts:AssumeRole"
        Principal = {
          Service = "lambda.amazonaws.com"
        }
      }
    ]
  })
}
```

No `Resource`, no `Sid` needed (single statement, nothing to disambiguate).
`principalService` is a fixed trait per service — Lambda always passes
`"lambda.amazonaws.com"`, same as `permissionType` in `types.ts`.

## AWS service principals — the exact strings AWS expects

Not just "the service's name" — each is a specific hostname-shaped string,
and getting it wrong means `AssumeRole`/the call being denied, not a helpful
error at `plan` time. Terraform doesn't validate these; AWS does, at apply
or runtime.

### IAM-role holders in this catalog (`permissionType: "IAM"`) — used as `Principal.Service` in `assume_role_policy`

| Service | Principal |
|---|---|
| Lambda | `lambda.amazonaws.com` |
| EC2 | `ec2.amazonaws.com` |

### Service principals in this catalog (`permissionType: "Service"`) — used as `Principal` in a *resource-based* policy (e.g. `aws_lambda_permission`), not a trust policy

| Service | Principal |
|---|---|
| S3 (event notifications) | `s3.amazonaws.com` |
| API Gateway V2 | `apigateway.amazonaws.com` — same principal for both REST and HTTP APIs, despite the `v2` in the resource name |

### Common ones not yet in this catalog, for when it grows

| Service | Principal |
|---|---|
| ECS (task role trust) | `ecs-tasks.amazonaws.com` — not `ecs.amazonaws.com`, which is a different (control-plane) principal |
| EventBridge | `events.amazonaws.com` |
| SNS | `sns.amazonaws.com` |

`SQS` and `DynamoDB` are `permissionType: "Passive"` in this catalog, so
neither ever appears as a `Principal` — the Streams/polling case routes
through the *caller's own* IAM policy instead (see
`edge-terraform-templates.md`'s DynamoDB → Lambda worked example), never a
resource-based permission naming `dynamodb.amazonaws.com`.
